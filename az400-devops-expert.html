🚀 Multi-Stage YAML CI/CD Pipeline Architecture

Production pipelines decouple build artifacts from release deployments across distinct stages with automated governance gates. 

trigger:
  branches:
    include:
      - main
      - release/*

stages:
- stage: BuildAndTest
  displayName: 'Stage 1: Build, Test & Scan'
  jobs:
  - job: CompileApp
    pool:
      vmImage: 'ubuntu-latest'
    steps:
    - task: DotNetCoreCLI@2
      displayName: 'Compile .NET Solution'
      inputs:
        command: 'build'
        configuration: 'Release'

    - task: DotNetCoreCLI@2
      displayName: 'Execute Unit Tests'
      inputs:
        command: 'test'
        projects: '**/*Tests.csproj'
        arguments: '--configuration Release --collect:"Code Coverage"'

    - task: SonarCloudPrepare@1
      displayName: 'Prepare Static Analysis'

- stage: DeployStaging
  displayName: 'Stage 2: Deploy to Staging'
  dependsOn: BuildAndTest
  jobs:
  - deployment: DeployWeb
    environment: 'Staging'
    strategy:
      runOnce:
        deploy:
          steps:
          - script: echo "Deploying containerized web app to Staging App Service"

- stage: DeployProduction
  displayName: 'Stage 3: Production Release'
  dependsOn: DeployStaging
  jobs:
  - deployment: DeployProd
    environment: 'Production' # Protected by manual approval gate & Azure Monitor alert checks
    strategy:
      runOnce:
        deploy:
          steps:
          - script: echo "Deploying to Production with zero-downtime swap"

📝 Realistic AZ-400 Practice Scenarios

Scenario 1: Automated Release Approval Gates

An enterprise releases updates to an Azure Kubernetes Service (AKS) cluster. Management mandates that after deploying to production, the pipeline must monitor Azure Monitor application error rates for 30 minutes. If HTTP 500 error rates exceed 1%, the pipeline must trigger an automated rollback.

Question: Which Azure DevOps feature natively satisfies this requirement without manual intervention?

  • A) Manual Intervention Task
  • B) Environment Deployment Gates configuring 'Query Azure Monitor Alerts' with evaluation duration
  • C) Sending an email to the on-call engineer
  • D) A bash script containing sleep 1800 inside the build stage
Click to view Answer & Detailed Technical Rationale
Correct Answer: B (Environment Deployment Gates configuring 'Query Azure Monitor Alerts')

Detailed Analysis:

  • Option B is CORRECT: Azure DevOps Environment Gates allow automated evaluation of external health criteria (such as Azure Monitor alerts, Work Item queries, or REST APIs) before or after deployments. Setting a gate to query Azure Monitor alerts over an evaluation duration ensures that if error rates spike, the deployment fails and triggers automated rollback procedures.
  • Option A is INCORRECT: Manual intervention pauses the pipeline waiting for a human click, violating automated continuous delivery principles.
  • Option C is INCORRECT: Email notifications do not automatically control pipeline execution.
  • Option D is INCORRECT: Sleeping a pipeline agent wastes billable minutes and cannot evaluate metric conditions dynamically.
