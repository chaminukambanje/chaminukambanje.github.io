🪟 Advanced T-SQL Window Functions & CTE Recursion

Window functions perform calculations across a set of table rows that are related to the current row without collapsing rows into a single group.

1. Ranking & Offset Analytics

-- Advanced window partitioning with framing
SELECT 
    CustomerID,
    OrderDate,
    OrderAmount,
    -- Running total calculated per customer ordered by date
    SUM(OrderAmount) OVER(
        PARTITION BY CustomerID 
        ORDER BY OrderDate 
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS CumulativeSpend,
    -- Compare current order with previous order amount
    LAG(OrderAmount, 1, 0.00) OVER(
        PARTITION BY CustomerID 
        ORDER BY OrderDate
    ) AS PriorOrderAmount,
    -- Rank customers within their geographic territory
    DENSE_RANK() OVER(
        PARTITION BY TerritoryID 
        ORDER BY OrderAmount DESC
    ) AS TerritorySpendRank
FROM Sales.SalesOrderHeader;

2. Recursive CTE for Bill of Materials (BOM)

WITH ProductBOM_CTE AS (
    -- Anchor member: Find top-level finished assembly product
    SELECT 
        ComponentID, 
        ParentAssemblyID, 
        QuantityPerAssembly, 
        1 AS BOM_Level
    FROM Production.BillOfMaterials
    WHERE ParentAssemblyID IS NULL AND ComponentID = 707
    
    UNION ALL
    
    -- Recursive member: Traverse sub-components
    SELECT 
        bom.ComponentID, 
        bom.ParentAssemblyID, 
        bom.QuantityPerAssembly, 
        cte.BOM_Level + 1
    FROM Production.BillOfMaterials bom
    INNER JOIN ProductBOM_CTE cte 
        ON bom.ParentAssemblyID = cte.ComponentID
)
SELECT * FROM ProductBOM_CTE
ORDER BY BOM_Level, ComponentID;

⏳ Temporal Tables & System-Versioned Audit Trails

Temporal tables provide built-in time-travel querying. SQL Server automatically tracks historical row modifications in a linked historical table without requiring custom triggers. 

-- 1. Create System-Versioned Temporal Table
CREATE TABLE dbo.EmployeeSalary (
    EmployeeID INT NOT NULL PRIMARY KEY CLUSTERED,
    Salary DECIMAL(10,2) NOT NULL,
    DepartmentCode VARCHAR(10) NOT NULL,
    SysStartTime DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN NOT NULL,
    SysEndTime DATETIME2 GENERATED ALWAYS AS ROW END HIDDEN NOT NULL,
    PERIOD FOR SYSTEM_TIME (SysStartTime, SysEndTime)
)
WITH (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.EmployeeSalary_History));

-- 2. Query historical salary as it was exactly on January 1st, 2026 at 09:00 UTC
SELECT EmployeeID, Salary, DepartmentCode
FROM dbo.EmployeeSalary
FOR SYSTEM_TIME AS OF '2026-01-01T09:00:00Z'
WHERE EmployeeID = 1042;

📊 Clustered Columnstore Indexes (CCI) & Analytics

Columnstore indexes store data column-by-column rather than row-by-row. By combining dictionary encoding, bit-packing, and 10x data compression, analytical aggregations scan only the specific columns needed, skipping unneeded column segments.

Rowgroup Architecture: Columnstore data is organized into rowgroups of up to 1,048,576 rows. Rows inserted via small transactional batches land in the row-based Delta Store (B-Tree). When the Delta Store reaches 1M rows, the background Tuple Mover compresses them into a columnar rowgroup.

🚀 In-Memory OLTP & Memory-Optimized Tables

In-Memory OLTP removes buffer pool overhead and latch contention by storing data entirely in non-paged memory, using lock-free multi-version concurrency control (MVCC). 

-- Create memory-optimized table with Hash Index
CREATE TABLE dbo.HighThroughputTelemetry (
    DeviceID INT NOT NULL,
    ReadingTimestamp DATETIME2 NOT NULL,
    MetricValue FLOAT NOT NULL,
    CONSTRAINT PK_Telemetry PRIMARY KEY NONCLUSTERED HASH (DeviceID, ReadingTimestamp)
    WITH (BUCKET_COUNT = 2000000)
)
WITH (MEMORY_OPTIMIZED = ON, DURABILITY = SCHEMA_AND_DATA);
Bucket Count Rule: Sizing the BUCKET_COUNT parameter correctly is critical. Set BUCKET_COUNT to 1x to 2x the anticipated number of distinct key values. Sizing too low leads to hash chain collisions and slow sequential scans; sizing too high wastes memory.

📝 Realistic MCSA SQL Practice Scenarios

Scenario 1: Window Framing with ROWS vs RANGE

A database developer writes a query calculating running totals: SUM(Amount) OVER(ORDER BY OrderDate). They notice severe performance degradation and high tempdb spill on a 10-million row table.

Question: Why does this occur, and what is the optimal query rewrite?

  • A) The default framing is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which creates an on-disk spool in tempdb to handle ties. Fix by specifying ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW.
  • B) Window functions cannot use indexes; the query must be rewritten as a cursor.
  • C) Replace SUM with COUNT.
  • D) Enable In-Memory OLTP on the table to bypass tempdb.
Click to view Answer & Detailed Technical Rationale
Correct Answer: A (Default RANGE framing creates tempdb spool; replace with ROWS)

Detailed Analysis:

  • Option A is CORRECT: In T-SQL, when ORDER BY is specified in an OVER() clause without an explicit window frame, the ANSI default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. Because RANGE must account for duplicate values (ties), SQL Server allocates an on-disk worktable in tempdb. In contrast, ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW evaluates row-by-row sequentially in memory without allocating a tempdb spool, running up to 100x faster.
  • Option B is INCORRECT: Cursors are notoriously slow row-by-row procedural constructs.
  • Option C is INCORRECT: COUNT does not calculate a spend total.
  • Option D is INCORRECT: In-Memory OLTP does not alter ANSI window framing semantics.
