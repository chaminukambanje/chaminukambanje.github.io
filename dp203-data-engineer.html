🏛️ Synapse Dedicated SQL Pools: MPP & 60 Distributions

Synapse Dedicated SQL Pools leverage a Massively Parallel Processing (MPP) architecture dividing database storage into exactly 60 fixed compute distributions.

Table Distribution Strategies

Distribution Type Storage Mechanism Optimal Workload & Table Size
Hash Distributed Deterministic hash function assigns rows across the 60 distributions based on a single Distribution Column. Large Fact Tables (> 60M rows). Eliminates data movement (shuffle) when joined on the hash column.
Replicated A complete copy of the table is maintained on each compute node. Small Dimension Tables (< 2 GB). Completely eliminates data broadcast overhead during star-schema joins.
Round-Robin Rows are distributed uniformly and sequentially across the 60 distributions. Staging Tables. Fastest possible data ingestion speed before transformation into permanent hash tables.
Choosing a Hash Distribution Column: Select a column with high cardinality (many distinct values), no data skew (values evenly distributed), and zero NULLs (all NULL rows land in distribution 1, creating severe performance bottlenecks).

⚡ Azure Databricks: OPTIMIZE & Z-Ordering

-- Optimize Delta table file sizes and co-locate related data to maximize data skipping
OPTIMIZE silver_sales_transactions
ZORDER BY (TransactionDate, CustomerRegion);

Z-Ordering creates a multidimensional space-filling curve, organizing data into Parquet files such that queries filtering on TransactionDate or CustomerRegion can skip over 90% of file reads based on column min/max statistics.

🌊 Azure Stream Analytics Windowing Functions

Window Type Behavior & Characteristics SQL Example Syntax
Tumbling Window Fixed length, non-overlapping, contiguous time segments. GROUP BY TumblingWindow(minute, 5)
Hopping Window Fixed length, overlapping time segments hopping forward by a specified interval. GROUP BY HoppingWindow(minute, 10, minute, 2)
Sliding Window Produces output only when an event enters or exits the window. HAVING COUNT(*) > 3 AND SlidingWindow(minute, 1)
Session Window Groups events arriving together, closing when an inactivity gap threshold is reached. GROUP BY SessionWindow(minute, 5, minute, 15)

📝 Realistic DP-203 Practice Scenarios

Scenario 1: Synapse Table Distribution Selection

An enterprise data warehouse team is designing a star schema in Synapse Dedicated SQL Pools. The FactSales table contains 450 million rows and is frequently joined to DimDate (3,650 rows) and DimCustomer (120,000 rows).

Question: Which distribution strategy should be implemented for FactSales and DimDate?

  • A) FactSales: Round-Robin; DimDate: Round-Robin
  • B) FactSales: Hash distributed on CustomerKey; DimDate: Replicated
  • C) FactSales: Replicated; DimDate: Hash distributed on DateKey
  • D) FactSales: Hash distributed on OrderDate; DimDate: Hash distributed on CustomerKey
Click to view Answer & Detailed Technical Rationale
Correct Answer: B (FactSales: Hash distributed; DimDate: Replicated)

Detailed Analysis:

  • Option B is CORRECT: Large fact tables (> 60M rows) should always use Hash Distribution to distribute rows evenly across the 60 compute nodes. Small dimension tables (< 2 GB, such as DimDate with only 3,650 rows) should use Replicated distribution. Replicating the small dimension table ensures that each compute node possesses a complete local copy, allowing joins to execute entirely in memory with zero network data movement (data broadcast or shuffle).
  • Option A is INCORRECT: Round-robin fact tables force expensive data shuffling during analytical joins.
  • Option C is INCORRECT: Replicating a 450-million-row fact table across 60 distributions would exhaust storage and degrade write performance drastically.
  • Option D is INCORRECT: Hash keys on fact and dimension tables must match the join condition to avoid data movement.
