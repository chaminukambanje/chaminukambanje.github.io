📘 Exam AZ-104 Scope & Enterprise Architecture

Exam AZ-104: Microsoft Azure Administrator validates the foundational and intermediate skills required to implement, manage, and monitor an organization’s Microsoft Azure environment, covering virtual networks, identity, compute, storage, and governance.

🌐 Azure Networking: Peering, Routing & Security

Virtual networking is the most heavily weighted and technically intricate domain on the AZ-104 exam.

1. VNet Peering & Gateway Transit Architecture

┌───────────────────────────┐ ┌───────────────────────────┐ │ Hub VNet (10.0.0.0/16) │ ◄── Peering 1 ──► │ Spoke 1 (10.1.0.0/16) │ │ - Azure Firewall │ │ - Workload Subnet │ │ - VPN / ER Gateway │ │ - Use Remote Gateways │ │ - Allow Gateway Transit │ └───────────────────────────┘ └─────────────┬─────────────┘ │ Peering 2 ▼ ┌───────────────────────────┐ │ Spoke 2 (10.2.0.0/16) │ │ - Database Subnet │ │ - Use Remote Gateways │ └───────────────────────────┘

Critical Peering Rules:

  • Non-Transitive: By default, Spoke 1 cannot communicate with Spoke 2 across Hub VNet peering. Traffic between spokes requires a Network Virtual Appliance (NVA) or Azure Firewall with User-Defined Routes (UDRs).
  • Gateway Transit: To allow spokes to use the Hub's VPN/ExpressRoute gateway, enable Allow gateway transit on the Hub VNet peering and Use remote gateways on the Spoke VNet peering.

2. Routing Priority & User-Defined Routes (UDR)

When multiple routes exist for a destination IP, Azure selects the route using Longest Prefix Match (LPM). For identical prefixes, priority is evaluated as follows:

  1. User-Defined Routes (UDR): Highest priority. Forces traffic through an NVA (e.g., Next Hop: Virtual Appliance 10.0.1.4).
  2. BGP Routes: Propagated via ExpressRoute or VPN gateways (unless route propagation is explicitly disabled).
  3. System Default Routes: Lowest priority (Local VNet, On-premises, Internet, None).

3. Network Security Groups (NSGs) Evaluation Rules

NSG rules are processed in priority order from 100 to 4096. As soon as traffic matches a rule, processing stops. Default rules (65000, 65001, 65500) cannot be deleted but can be overridden by creating rules with lower priority numbers.

2. Shared Access Signatures (SAS) Security

SAS Type Signing Mechanism Security Best Practice
User Delegation SAS Signed using Entra ID (Azure AD) user credentials. Most Secure (Recommended). Revoking the Entra ID user token or role assignment immediately revokes the SAS without rotating storage account keys.
Service SAS Signed using Storage Account Access Keys. Scoped to a single resource. Should always be linked to a Stored Access Policy on blob containers to enable immediate revocation.
Account SAS Signed using Storage Account Access Keys. Grants access to account-level operations. Least secure; rotating account keys invalidates all issued Account SAS tokens.

🛡️ Microsoft Entra ID, PIM & Governance

Privileged Identity Management (PIM)

  • Eligible vs Active: Users are assigned Eligible status, requiring step-up authentication (MFA, justification, approval ticket) to activate roles for a limited duration (e.g. 4 hours).
  • Access Reviews: Automated periodic certification of user access rights to maintain least-privilege compliance.

Azure Policy & Resource Hierarchy

  • Hierarchy: Root Management Group -> Child Management Groups -> Subscriptions -> Resource Groups -> Resources.
  • Policy Effects: Deny (blocks creation), Audit (logs non-compliance), DeployIfNotExists (automatically provisions missing extensions/monitoring).

📝 Realistic AZ-104 Practice Scenarios

Scenario 1: Non-Transitive VNet Peering Communication

An administrator establishes VNet peering between VNet-A and VNet-B, and between VNet-B and VNet-C. Virtual machines in VNet-A can communicate with VNet-B, and VNet-B can communicate with VNet-C. However, VMs in VNet-A cannot communicate with VMs in VNet-C.

Question: Why does this occur and how can direct connectivity be established?

  • A) NSGs on VNet-C are blocking ICMP; add an allow rule for port 443.
  • B) VNet peering is non-transitive. To connect VNet-A and VNet-C directly, you must configure a direct VNet peering between VNet-A and VNet-C, or deploy an NVA in VNet-B with User-Defined Routes.
  • C) Gateway transit must be disabled on VNet-B.
  • D) Subnets across the three VNets have overlapping IP ranges.
Click to view Answer & Detailed Technical Rationale
Correct Answer: B (VNet peering is non-transitive; peer A and C directly or deploy NVA with UDRs)

Detailed Analysis:

  • Option B is CORRECT: In Azure, VNet peering relationships are strictly non-transitive. Traffic will not route through an intermediate peered VNet without a routing device. Connectivity between VNet-A and VNet-C requires either: 1) A direct peering between VNet-A and VNet-C, or 2) Deploying a Network Virtual Appliance (NVA) / Azure Firewall in VNet-B and assigning User-Defined Route (UDR) route tables on VNet-A subnets setting Next Hop = Virtual Appliance (VNet-B NVA IP).
  • Option A is INCORRECT: Port 443 is HTTPS; ICMP uses protocol 1. Furthermore, routing must exist before NSGs are evaluated.
  • Option C is INCORRECT: Gateway transit controls VPN/ExpressRoute gateway sharing, not spoke-to-spoke routing.
  • Option D is INCORRECT: Azure prevents creation of VNet peering between VNets with overlapping IP address spaces.
